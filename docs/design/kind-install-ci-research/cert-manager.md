# cert-manager: installing kind in CI

## TL;DR

cert-manager does NOT use `helm/kind-action`, `engineerd/setup-kind`, or `go install sigs.k8s.io/kind`.
It downloads a prebuilt kind release binary with `curl` from GitHub releases, then verifies a pinned SHA256.
The same pattern provisions kubectl (from dl.k8s.io) and helm (from get.helm.sh).
The action never creates the cluster. A Makefile target runs `make/cluster.sh`, which calls `kind create cluster` itself.
Versions live as `tool=vX.Y.Z` lines in a vendored makefile-modules file, kept fresh by Renovate.
E2E does not run in GitHub Actions at all. It runs on Prow via `make/e2e-ci.sh`. The only GitHub Actions workflows are govulncheck and scorecards.

## How it works

The tool machinery is a vendored Makefile module from `cert-manager/makefile-modules`, cloned into `make/_shared/tools` and pinned by commit hash in `klone.yaml`.

Each tool is declared as `tools += name=version` in `make/_shared/tools/00_mod.mk`. Current pins: `kind=v0.32.0`, `kubectl=v1.36.2`, `helm=v4.2.2`. The module generates `$(KIND_VERSION)`, `$(NEEDS_KIND)`, and `$(KIND)` variables per tool.

Download recipes curl the binary and pass it through `checkhash.sh`, which fails the build on a SHA256 mismatch:
- kind: `curl https://github.com/kubernetes-sigs/kind/releases/download/$(KIND_VERSION)/kind-$(HOST_OS)-$(HOST_ARCH)` then check `kind_$(HOST_OS)_$(HOST_ARCH)_SHA256SUM`.
- kubectl: `curl https://dl.k8s.io/release/$(KUBECTL_VERSION)/bin/$(HOST_OS)/$(HOST_ARCH)/kubectl` then checkhash.
- helm: `curl https://get.helm.sh/helm-$(HELM_VERSION)-$(HOST_OS)-$(HOST_ARCH).tar.gz`, checkhash the tarball, extract the binary.

Binaries land in `$(DOWNLOAD_DIR)/tools` and are symlinked into `bin/tools`, which is prepended to PATH so the pinned versions always win.

Cluster creation is separate from binary install. `make e2e-setup-kind` depends on `$(NEEDS_KIND)` (install) and then runs `make/cluster.sh`, which calls `kind create cluster --config make/config/kind/cluster.yaml --image "$image" --name "$name"`. The `$image` is a `kindest/node` reference pinned by digest, selected by K8S version from `make/kind_images.sh` (regenerated by `hack/latest-kind-images.sh`).

Version reproducibility has three layers: the `tools +=` version pins, the per-platform SHA256 constants next to each recipe, and Renovate (`.github/renovate.json5`) with `# renovate:` datasource comments that automate the bumps. Node image digests are pinned separately in `make/kind_images.sh`.

## Relevance to Karta

Karta also uses Go 1.25, controller-runtime, and Helm, and wants reproducible e2e. cert-manager shows a self-contained, hermetic pattern that does not depend on any Marketplace action, and that verifies every downloaded binary by checksum. It also shows a clean separation: install the kind binary via make, create the cluster via a script you control, so the same command runs identically locally and in CI.

## Lessons for Karta

- Install kind, kubectl, and helm as pinned binaries with curl plus a mandatory SHA256 check. Do not trust a Marketplace action to pick versions.
- Keep binary install separate from cluster creation. Let make install the binary; let a script you own run `kind create cluster`. Same behavior locally and in CI.
- Pin the kind `kindest/node` image by digest per Kubernetes minor version, separate from the kind binary version.
- Put every tool version in one place with `# renovate:` markers so a bot can raise version-bump PRs, and re-check the checksum on bump.
- Prepend your tools dir to PATH so the pinned binary always wins over whatever the runner ships.

## What NOT to copy

- The Prow-based e2e harness. Karta is a standard GitHub project, so Karta wants e2e in GitHub Actions, not Prow. Only the tool-install and cluster-creation mechanics transfer.
- The full vendored makefile-modules system (`klone.yaml`, `make/_shared`) is heavyweight. Karta can adopt just the curl-plus-checkhash idea without cloning the whole module framework.
- Parsing kind release notes to extract node-image digests (`hack/latest-kind-images.sh`) is fragile by cert-manager's own admission. Prefer a more robust digest source if one exists.
