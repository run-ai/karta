# opencost: attributing per-pod telemetry to workloads

## TL;DR

- OpenCost is a query-Prometheus-and-join engine. For each window it fires roughly 40 parallel PromQL queries (CPU, RAM, GPU, network, PV, labels, owners), decodes them into typed results, and joins them in Go on a (cluster, namespace, pod) key into a per-container allocation map.
- Pod-to-workload resolution is not done by walking ownerReferences at attribution time. It joins metric series: kube_pod_owner for DaemonSet/Job/ReplicaSet kinds, a one-level ReplicaSet-to-Deployment/Rollout hop via kube_replicaset_owner, and label-selector matching (deployment_match_labels vs pod labels) for Deployments and StatefulSets. Anything else falls to unallocated on the develop branch.
- OpenCost also runs its own metric exporter, but only to fill gaps kube-state-metrics does not cover (owner refs, match labels, per-container cost/allocation gauges, node prices). It scrapes its own emissions back out of Prometheus later. Workload-level aggregates are never re-emitted as Prometheus series; they are served from an HTTP API (/allocation/compute?aggregate=controller).
- GPU attribution joins DCGM_FI_PROF_GR_ENGINE_ACTIVE by (container, pod, namespace) directly; it relies on dcgm-exporter's pod labels being correct and detects shared GPUs via the nvidia_com_gpu_shared resource request.
- The newer collector-source module is OpenCost's own verdict on the Prometheus-join costs: it bypasses Prometheus and scrapes kubelet /stats/summary and dcgm-exporter pods directly, on a 30s default interval, discovering targets from an informer-backed cluster cache.

## How it works

Architecture: both Prometheus queries and API-server watching, for different jobs.
An informer-style cluster cache (pkg/clustercache/clustercache.go, core/pkg/clustercache/clustercache.go) watches pods, nodes, deployments, replicasets, jobs, and more. The metric exporter (pkg/metrics/*.go, registered in pkg/metrics/kubemetrics.go) reads that cache on every Prometheus scrape and emits kube-state-metrics-shaped series: kube_pod_owner from pod.OwnerReferences (pkg/metrics/podmetrics.go, lines 144-146), deployment_match_labels from deployment selectors (pkg/metrics/deploymentmetrics.go). A second emitter, CostModelMetricsEmitter (pkg/costmodel/metrics.go), loops every minute (line 861) computing current prices and per-container allocation, and sets gauges such as container_cpu_allocation, container_gpu_allocation, and node_gpu_count, all labeled by namespace, pod, container, node (lines 200-230).

Attribution happens later, offline, by querying Prometheus. ComputeAllocation (pkg/costmodel/allocation.go) splits the window into batches capped by PROMETHEUS_MAX_QUERY_DURATION_MINUTES (default one day, modules/prometheus-source/pkg/env/promenv.go line 170). Per batch, computeAllocation first builds a pod map from a kube_pod_container_status_running uptime query (pkg/costmodel/allocation_helpers.go buildPodMap, with a 3-retry loop), then launches the full query group (allocation.go lines 272-361): usage (container_cpu_usage_seconds_total rate, container_memory_working_set_bytes), requests/limits (kube_pod_container_resource_requests), its own allocation gauges, GPU series, labels, annotations, and owner series. All PromQL strings live in modules/prometheus-source/pkg/prom/metricsquerier.go. Results are folded into the pod map by pure-Go apply functions keyed on (cluster, namespace, pod) with an optional pod-UID disambiguation map for name collisions (allocation.go lines 241-254).

Controller resolution (allocation.go lines 483-496): Deployments and StatefulSets are matched by evaluating selector labels against pod labels in-app (labelsToPodControllerMap); DaemonSets and Jobs come from kube_pod_owner{owner_kind="..."} queries; ReplicaSets get one level of owner walking in PromQL space (kube_replicaset_owner with owner_kind="<none>" or "Rollout", resToPodReplicaSetMap in allocation_helpers.go lines 1501-1573). Later maps overwrite earlier ones via applyControllersToPods. On develop, a pod owned by any other kind (PyTorchJob, RayCluster) stays unattributed; the local branch here adds a generic any-owner base layer from kube_pod_owner (resToPodAnyOwnerMap) precisely because of that gap.

GPU: usage avg/max come from avg/max_over_time of DCGM_FI_PROF_GR_ENGINE_ACTIVE grouped by (container, pod, namespace) (metricsquerier.go lines 1184, 1202); requested GPUs from kube_pod_container_resource_requests{resource="nvidia_com_gpu"}; allocated from OpenCost's own container_gpu_allocation gauge; shared-GPU detection from the nvidia_com_gpu_shared resource name (allocation_helpers.go applyGPUUsageShared, lines 810-827). The join is by pod and container name only, so it inherits whatever pod attribution dcgm-exporter performed at scrape time.

Output: computed AllocationSets are served over HTTP (pkg/costmodel/router.go line 578, /allocation/compute) and aggregated on demand by properties including controller and controllerkind (core/pkg/opencost/allocationprops.go line 80, core/pkg/opencost/allocation.go AggregateBy). No attributed workload-level Prometheus series are exposed.

Costs of the approach, as visible in the code: default query resolution is 5m and the comment says finer resolution is "more computationally expensive" (promenv.go lines 112-119); query concurrency is capped at 5 with 429 retry logic (promenv.go lines 122-129, 49-64); the CPU max query needs either a pre-installed recording rule or an expensive subquery fallback (metricsquerier.go lines 1107-1132, warning in allocation.go line 290); a single failed query in the group fails the whole allocation computation (allocation.go lines 428-434); stale gauge series must be manually deleted when pods churn or data goes wrong (metrics.go lines 815-825); Prometheus label sanitization forces hyphen/underscore de-duplication heuristics (allocation_helpers.go lines 1606-1616); and same-named pods need UID ingestion plus a many-to-one key map to avoid double counting (allocation.go lines 241-254, comment at lines 461-464). Freshness is bounded by scrape interval plus resolution plus emitter lag, since half the joined series are OpenCost's own emissions round-tripped through Prometheus. The collector-source module removes that round trip: it discovers dcgm-exporter pods by label from the cluster cache and scrapes podIP:9400/metrics directly (modules/collector-source/pkg/scrape/dcgm.go), pulls CPU/RAM from kubelet /stats/summary (modules/collector-source/pkg/scrape/statsummary.go), on a 30s default interval (modules/collector-source/pkg/env/collectorenv.go line 30).

## Relevance to Karta

Karta's exporter has the same shape as OpenCost's attribution core: take per-pod series (DCGM, metrics-server) and re-key them to a higher-level owner. OpenCost proves the join is workable but shows it costs a whole subsystem: an owner-metric exporter, a query engine with batching and rate limiting, and name-collision handling. Karta already holds the piece OpenCost has to reconstruct from metrics: the workload-to-component-to-pod mapping, live, from its CRD and pod selectors. That means Karta can do the join at scrape time in-process (OpenCost's collector-source direction, which even defaults to Karta's target 30s), instead of OpenCost's historical query-and-join direction. OpenCost's HTTP-API-not-metrics choice does not fit Karta's goal of re-exposing Prometheus series, but its emitter code is directly relevant to doing that safely (stale series deletion, disabled-metrics config).

## Lessons for Karta

- Do the pod-to-workload join where the mapping already lives. OpenCost burns queries and code re-deriving ownership from metric series because Prometheus is its only source of history. Karta's CRD already knows workload, component, and pod selector; attribution can be a map lookup at collection time.
- Attribute by pod UID, not pod name. OpenCost's IngestPodUID machinery and its "two pods with the same name" double-counting caveat exist because name-keyed joins are ambiguous across pod restarts within a window.
- If scraping sources directly, follow collector-source: discover dcgm-exporter endpoints from an informer cache and scrape at 30s; pull CPU/RAM from kubelet stats. This is exactly Karta's target resolution and avoids Prometheus freshness lag.
- When re-emitting gauges keyed by dynamic objects, delete stale label sets on churn (OpenCost tracks containerSeen/nodeSeen maps and calls DeleteLabelValues) and make every emitted metric individually disableable (disabledMetrics config).
- Handle non-controller and multi-hop owners deliberately: use only the controller ownerReference, and collapse pod - ReplicaSet - Deployment/Rollout to the top workload, or dashboards fragment per ReplicaSet.
- Design for generic owner kinds from day one. OpenCost's per-kind queries left every workload CRD unattributed; the fix (a generic base layer overridden by specific resolvers) had to be retrofitted.

## What NOT to copy

- The Prometheus round trip for cluster state: emitting owner and selector metrics, waiting for Prometheus to scrape them, then querying them back. Karta watches the API server already; joining through a TSDB adds lag, query load, and a hard dependency.
- Label-selector matching as the Deployment/StatefulSet attribution mechanism. It re-implements selector semantics on sanitized Prometheus labels and needs hyphen/underscore de-dup hacks; ownerReferences (or Karta's componentization) are authoritative.
- All-or-nothing query groups: one failed sub-query aborts the whole allocation window. A 30s exporter should degrade per-signal (emit CPU even if DCGM is down) rather than fail closed.
- 5m default resolution with expensive subquery fallbacks and recording-rule prerequisites. That design is shaped by cost reporting over days; it cannot cheaply hit 30s, which is why OpenCost itself built collector-source.
- Serving attribution only via a bespoke HTTP API. Fine for a cost UI, but it forfeits the Prometheus ecosystem (recording rules, alerts, Grafana) that Karta's exporter is meant to feed.
