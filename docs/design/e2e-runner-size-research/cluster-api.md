# cluster-api: e2e runner specs

## TL;DR

Cluster API (kubernetes-sigs/cluster-api) does NOT run its kind-based e2e
tests on GitHub Actions. GitHub Actions in this repo is used only for
lint, verify, unit-test-release, link checks, and release automation, all
on `ubuntu-latest` (GitHub hosted-small). The real e2e suite runs on the
Kubernetes project's external Prow / GCB infrastructure, and the concrete
job definitions (including any CPU/memory resource requests and machine
sizing) live in the separate kubernetes/test-infra repo, NOT in this repo.

The only machine size expressed inside this repo is for image build jobs
on Google Cloud Build: `machineType: 'E2_HIGHCPU_8'` (GCP e2-highcpu-8,
8 vCPU) in `cloudbuild.yaml` and `cloudbuild-nightly.yaml`. Those are
release-staging image builds, not the e2e test jobs. The e2e parallelism
knob that this repo does control is `GINKGO_NODES=3` in
`scripts/ci-e2e.sh` (Makefile default is `GINKGO_NODES ?= 1`).

Category: external-Prow (Kubernetes test-infra), with GitHub Actions used
only for hosted-small non-e2e checks.

## How it works

1. GitHub Actions (`.github/workflows/`) covers only non-e2e checks. Every
   workflow job is `runs-on: ubuntu-latest`. None of them stand up kind or
   run the e2e suite.

2. The kind-based e2e suite is driven by `scripts/ci-e2e.sh`, which builds
   the CAPI/CAPD docker images and runs Ginkgo against a kind-hosted
   management cluster (`USE_EXISTING_CLUSTER=false`, docker infrastructure
   provider). It sets `GINKGO_NODES=3`. This script is invoked by Prow
   jobs, not by anything in `.github/`.

3. The Prow job definitions are generated by an in-repo tool
   (`hack/tools/prowjob-gen`) but WRITTEN INTO the external test-infra
   repo. The Makefile target `generate-test-infra-prowjobs` reads its
   config and templates from `$(TEST_INFRA_DIR)` and writes output there.
   So the file that would carry the actual e2e machine size / resource
   requests (`cluster-api-prowjob-gen.yaml` and the `templates/` dir) is
   under `config/jobs/kubernetes-sigs/cluster-api/` in kubernetes/test-infra,
   which is not part of this repo.

4. The `cloudbuild.yaml` / `cloudbuild-nightly.yaml` files use GCB
   `machineType: 'E2_HIGHCPU_8'`, but only for `make release-staging` /
   `release-staging-nightly` image builds, not for the e2e tests.

## Relevance to Karta

Karta currently runs its kind-based e2e on GitHub Actions (the `e2e-karta`
branch work). Cluster API is a useful contrast point: a very large CAPI
e2e suite does NOT fit GitHub hosted runners and was pushed to external
Prow/GCB with explicit Ginkgo parallelism. The only in-repo machine sizing
that is meaningful for Karta is the pattern of controlling Ginkgo node
count (`GINKGO_NODES`) and, for image builds, choosing an 8-vCPU GCB
machine. Karta does not have (and likely does not want) the Prow
dependency, so the direct machineType/resource numbers here are not
transplantable.

## Lessons for Karta

- Separate concerns: keep fast checks (lint, unit, verify) on cheap hosted
  runners (`ubuntu-latest`), and treat heavy kind-based e2e as a distinct
  job class with its own sizing decision.
- Make Ginkgo parallelism an explicit, tunable knob (`GINKGO_NODES`), with
  a conservative default (CAPI defaults to 1, bumps to 3 in CI). This lets
  runner size and parallelism be tuned together without code changes.
- For image builds specifically, an 8-vCPU class machine (GCB
  e2-highcpu-8) was chosen by a large project - a reasonable reference
  point if Karta ever needs a bigger builder.

## What NOT to copy

- Do not adopt the Prow / kubernetes-test-infra dependency. CAPI's real
  e2e sizing lives outside the repo in that shared infra; Karta has no
  reason to take on that operational surface.
- Do not read `E2_HIGHCPU_8` as the e2e test machine size. It is an image
  build machine in `cloudbuild.yaml`, not the kind-e2e job.
- Do not assume any CPU/memory resource requests exist in-repo. They do
  not; copying "the numbers" from this repo is impossible because the
  numbers are in kubernetes/test-infra.
